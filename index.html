配置

git config --global user.email "邮箱"设置全局邮箱
git config --global --list查看所有全局配置

仓库初始化
git init在当前目录初始化新仓库
git clone <url>克隆远程仓库到本地，自动设置 origin
暂存与提交
git status查看工作区和暂存区状态，养成 commit 前先 status 的习惯
git add <文件>暂存指定文件
git add .暂存「当前目录及子目录」的改动，受所在目录限制
git add -A暂存「整个仓库」的改动，不管你 cd 到哪，最稳
git add -p交互式挑选，把同一个文件里的「部分改动」分开暂存（p=patch）
git commit -m "message"提交，message 格式：feat/fix/docs/style/chore: 描述
git commit -am "message"暂存+提交一步走，但 -a 只对「已跟踪」文件有效，新文件带不上
git commit --amend --no-edit补文件进上一个提交但不改 message（先 git add 漏掉的文件）
git commit --amend -m "新message"同时改上一个提交的内容和 message（仅限未 push）
.gitignore
在仓库根目录建 .gitignore 文件，每行一条规则，并要把它本身提交，否则队友那边不生效规则示例 ↓
node_modules/忽略整个目录
*.log忽略所有 .log 文件
.env忽略密钥/环境变量文件（重要）
git rm --cached <文件>关键坑：已被跟踪的文件，光写 .gitignore 挡不住，要先 rm --cached 取消跟踪
查看历史与排查
git log --oneline简洁查看提交历史
git log --oneline --graph --all图形化显示所有分支历史，最常用
git log --oneline -- <文件>只看动过某个文件的提交（-- 分隔路径，防止和分支名混淆）
git log -p <文件>连每次的具体改动一起看
git blame <文件>逐行追溯：每行最后是谁、哪个提交、何时改的。排查 bug 神器
git show <提交ID>查看某一个提交的完整改动内容
git diff工作区 vs 暂存区（改了还没 add 的）
git diff --staged暂存区 vs 上次提交（已 add 还没 commit 的）。=--cached
git diff HEAD所有未提交改动 vs 上次提交（工作区+暂存区一起比）
git reflogHEAD 移动日记，终极后悔药（详见补救页）
git bisect（二分查 bug）
用途：在几十上百个提交里，快速定位是哪个提交引入了 bug。二分法，100 个提交约 7 次即可锁定流程 ↓
git bisect start1. 开始二分
git bisect bad2. 标记当前版本是「坏的」
git bisect good <旧ID>3. 标记某个确定「好的」旧版本
Git 自动跳到中间点，你测试后回答 git bisect good 或 git bisect bad，反复几轮4. 二分定位
git bisect reset5. 结束，回到正常状态
分支操作
git branch查看所有本地分支
git branch -a查看所有分支（含远程追踪）
git switch -c <分支名>创建并切换到新分支
git switch <分支名>切换到已有分支
git branch -d <分支名>删除已合并的分支（安全）
git branch -D <分支名>强制删除分支（未合并也删）
git branch -m <旧名> <新名>重命名分支
合并
git merge <分支名>把指定分支合并进当前分支
git merge --no-ff <分支名>强制产生合并提交，不 fast-forward
变基
git rebase <分支名>把当前分支变基到指定分支，保持线性历史
git rebase --continue解决冲突后继续 rebase
git rebase --abort放弃 rebase，恢复原状
git rebase -i HEAD~n交互式 rebase，整理最近 n 个提交
冲突解决步骤
1. 打开冲突文件，找到 <<<<<<< ======= >>>>>>> 标记三个标记之间是两个版本的内容
2. 手动编辑，保留最终想要的内容，删掉所有标记VS Code 点击按钮或直接编辑均可
git add <冲突文件>3. 标记冲突已解决（merge 和 rebase 都要这步）
git commit4a. merge 时：完成合并提交（不用 -m，Git 自动填信息）
git rebase --continue4b. rebase 时：继续重放下一个提交
⚠ rebase 冲突时 HEAD 方向是反的
merge 冲突时：<<< HEAD 一侧 = 你当前分支；>>> 一侧 = 被合进来的分支。符合直觉正常方向
rebase 冲突时：<<< HEAD 一侧 = 你正变基到的「目标基底」（如 main）；>>> 一侧 = 你自己正被重放的那个提交。方向反了！易错！
原因：rebase 是把你的提交逐个「贴」到目标分支上，已在底下的目标才是 HEAD，你的改动反而是「传入的一侧」记住这句
stash（临时存改动）
git stash把当前改动暂存起来、工作区变干净，用于临时切分支。只存「已跟踪」文件
git stash -u连未跟踪的新文件一起 stash
git stash list查看所有 stash 记录
git stash pop恢复最近一条并从列表删除
git stash apply恢复但保留记录（可恢复到多个分支）
git stash pop stash@{2}恢复指定的某一条
merge vs rebase：公共/共享分支合并用 merge，本地私有分支整理历史、PR 前同步主分支用 rebase。
黄金法则：判断能不能 rebase 看的不是分支名，而是「改了之后会不会有别人手里的历史对不上」。已 push 且别人在用 = 公共 = 绝不 rebase。
共享 feature 分支（你和同事一起开发同一分支）同步 main 要用 git merge main，不能 rebase，否则同事的历史会对不上。
远程管理
git remote add origin <url>添加远程仓库，起别名 origin
git remote -v查看远程仓库地址
git remote set-url origin <url>修改已有远程地址（如从 HTTPS 换 SSH）
推送与拉取
git push -u origin main首次推送并设上游。-u 绑定是「单个分支」级别，只绑 main↔origin/main
git push推送到已设置的上游
git push -u origin <分支名>推送新分支并绑上游。每个新分支都要单独设一次
git branch -vv查看每个分支绑定的上游，后面 [origin/xxx] 就是
git config --global push.autoSetupRemote true配一次后，新分支首次 git push 自动建远程分支并绑上游，省去 -u
git fetch origin只下载远程最新状态，不合并，先看后合
git pull origin mainfetch + merge，会产生合并提交
git pull --rebase origin mainfetch + rebase，保持线性历史，团队推荐
git push --force-with-leaserebase 过私有分支后推送用它，比 --force 安全：会检查远程有没有别人的新提交
裸 git pull 能用吗？取决于「当前分支有没有上游」，而非有没有 push 过。上游来源有三：① git clone 自动设的 ② push -u 设的 ③ git branch --set-upstream-to=origin/main 手动设的。一个都没设过，就必须写全 git pull origin <分支>。
push 被拒绝的标准处理
git pull --rebase origin main第一步：先同步远程
如有冲突，解决后 git rebase --continue第二步：处理冲突
git push第三步：再推送

PR 与 Issue 关联
在 PR 描述或某条 commit message 里写关键字，PR 合并进 main 时自动关闭对应 issue写法 ↓
closes #12close / closes / closed 均可
fixes #12fix / fixes / fixed 均可
resolves #12resolve / resolves / resolved 均可
Code Review 后按意见改，再 push 到同一 feature 分支，PR 会自动更新，不用重开迭代方式
GitHub Actions 是什么
GitHub 的自动化流水线（CI/CD）。在 .github/workflows/ 放 yml 配置，指定「当 push 或开 PR 时」自动跑某些任务作用
常见用途：自动跑测试、检查代码风格、自动构建部署。PR 页面会显示 ✓ 或 ✗，红叉就是某项检查没过知道即可
撤销选择指南
git restore <文件>还没 add → 丢弃工作区改动（不可恢复，危险）
git restore --staged <文件>已经 add → 移出暂存区，改动保留（安全）
git commit --amend刚提交写错了 → 修改最后一次提交（未推送时用）
git reset --soft HEAD~n撤销 n 个提交，改动留在暂存区
git reset --mixed HEAD~n撤销 n 个提交，改动留在工作区（默认）
git reset --hard HEAD~n撤销 n 个提交，改动直接丢弃（危险）
git revert <提交ID>已推送的提交 → 创建新提交抵消，不改历史（安全）
reflog 救命流程
git reflog查看所有操作历史，数字越小越新
看描述找到误操作前的那一行，复制那个提交 ID靠描述定位，不要数序号
git reset --hard <ID>恢复到那个状态（reset 误操作）
git switch -c <分支名> <ID>从那个 ID 重建分支（误删分支）
记住：只要 commit 过，90 天内几乎都能用 reflog 找回来。reset --hard 和 restore 是真正危险的操作，执行前想清楚。

核心概念辨析

reset 三种模式
git reset --soft HEAD~n退到「待提交」：改动留在暂存区
git reset --mixed HEAD~n退到「待暂存」：改动留在工作区，暂存区也被清空（默认模式）
git reset --hard HEAD~n全部抹掉：工作区+暂存区的改动都丢弃（危险）
reset vs revert
reset：把分支指针往回挪，会「删除/重写」历史。只能用于未推送的本地提交改历史
revert：新建一个「反向补丁」提交来抵消，历史只增不改。已 push 的公共提交必须用它不改历史
为什么公共提交不能用 reset：重写历史会让其他协作者本地历史对不上，再 pull 一团乱原因
merge vs rebase
merge：找共同祖先，两边改动一次性融合，产生一个合并提交，历史留分叉。冲突只解决一次保留真实历史
rebase：把当前分支的提交逐个「重放」到目标后面，不产生合并提交，历史是直线。提交 ID 全部重写，可能要解决多次冲突线性历史
rebase 改的是当前分支的提交 ID，目标分支（如 main）完全不受影响关键
fast-forward 是什么
当 main 的历史完全包含在 feature 里（没分叉），merge 时 Git 只是把 main 指针往前挪到 feature 位置移动指针
不产生新提交、不修改文件、不可能冲突，因为根本没有「融合」动作发生所以无冲突
git merge --no-ff强制产生合并提交，即使能 ff 也保留一个分支汇合点
reflog 原理
reflog 是「HEAD 移动的日记本」，记录指针去过哪些提交 ID。reset --hard 删掉的提交其实没真删，只是没分支指向它，成了「悬空对象」躺在 .git 里能救命的原理
特性：① 本地私有，不会 push 也不随 clone ② 自动过期（可达 90 天 / 不可达 30 天）③ 出事要趁早救三个特性
三个区域 / 三类文件状态
工作区（你编辑的文件）→ git add → 暂存区（待提交快照）→ git commit → 版本库（历史）数据流向
untracked（新文件，Git 没管过）→ add 后变 tracked。-a 和 .gitignore 的很多坑都源于这个区别跟踪状态

VS Code 里怎么操作（对照命令行）

理解 GUI 背后执行了什么命令，比单纯记按钮重要。下面每个操作都给出对应的命令行等价物。
Source Control 面板
左侧分支图标（或 Ctrl/Cmd+Shift+G）打开。改动的文件列在 Changes 下≈ git status
文件旁点 + 号 = 暂存该文件；点文件名看左右对比 diff≈ git add / git diff
顶部输入框写 message，点 ✓ Commit≈ git commit -m
untracked 新文件带 U 标记，单独列出。提交前扫一眼别漏注意
⚠ 没暂存直接 Commit 的行为
没点任何 + 就按 Commit，VS Code 弹窗问是否「暂存所有改动并提交」，点 Yes 等价于 git commit -a≈ commit -a
关键：这只包含「已跟踪」文件，全新的 untracked 文件不会被带进去，必须先手动点 + 暂存易踩坑
设置项 git.enableSmartCommit 开了就不再弹窗，但新手建议关着，弹窗能提醒你别漏暂存建议

状态栏的 ↑↓ 同步箭头 = 推送/拉取，数字表示领先/落后远程几个提交≈ git push / pull
解决冲突（三方对比界面）
合并冲突时，冲突文件标红。打开后每段冲突上方有可点的按钮可视化解决

点 Resolve in Merge Editor 进三方对比：左=当前、右=传入、下=最终结果，勾选要的部分推荐

遇到问题怎么办

push 被拒绝，提示 remote contains work...
git pull --rebase origin main → 解决冲突（如有）→ git push
合并出现冲突，有 <<<<<<< 标记
打开文件手动编辑保留最终内容，删掉所有标记 → git add 文件 → git commit
刚提交完发现漏加了一个文件 / message 写错
未推送：git add 漏掉的文件 → git commit --amend --no-edit（只补文件）或 git commit --amend -m "新message"（连 message 一起改）
想把一个文件里的部分改动分开提交
git add -p 交互式挑选要暂存的代码块，分多次 commit
改到一半要紧急切分支修 bug
git stash（有新文件用 git stash -u）→ 切分支修好提交 → 切回来 git stash pop
和同事共享同一个 feature 分支，要同步 main
git pull（先拉同事的）→ git merge main。不能用 rebase，否则同事历史对不上
不知道是哪个提交引入了 bug
git bisect start → git bisect bad → git bisect good 旧ID → 二分测试 → git bisect reset
想知道某一行代码是谁、何时改的
git blame 文件名，或在 VS Code 装 GitLens 看行内提示
rebase 私有分支后 push 被拒
git push --force-with-lease（比 --force 安全，会检查远程有没有别人的新提交）
不小心把已被跟踪的文件加进 .gitignore 却没生效
git rm --cached 文件 取消跟踪，再提交。.gitignore 只能挡没被跟踪过的文件
误用 reset --hard 删掉了提交
git reflog 找到误操作前的 ID → git reset --hard <ID>
误删了分支
git reflog 找到该分支最后一个提交 ID → git switch -c 分支名 <ID>
已推送的提交有 bug 需要撤销
git revert <提交ID> → git push（不改历史，安全）
想把队友的最新 main 同步到我的 feature 分支
git switch feature/xxx → git pull --rebase origin main
不小心在 main 上做了修改没提交
git stash 暂存改动 → git switch -c feature/xxx → git stash pop 恢复改动
想参与开源项目
Fork → Clone → git remote add upstream <原始仓库> → 开分支开发 → 提 PR
把密码文件提交了
立刻撤销密钥 → git filter-repo --path 文件 --invert-paths → force push → 团队重新 clone
